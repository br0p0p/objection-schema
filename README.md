# objection-schema

Schema-first, class-free models for [objection.js](https://vincit.github.io/objection.js) 3.x.
Columns are [Standard Schema](https://standardschema.dev) validators (zod, valibot, arktype, …), and
row, insert, patch, relation and query result types are inferred from them. Under the hood each
definition is an ordinary objection `Model` subclass, so it works with existing class-based models,
query builders, transactions and plugins.

> **Status:** 0.1.0, private, exploratory. It grew out of an exploration branch of objection itself;
> the design notes and history are in the `objection-typed-exploration` repo (PR #1).

```ts
import { column, defineModel, defineModels } from 'objection-schema';
import { z } from 'zod';

const Person = defineModel({
  table: 'persons',
  columns: {
    id: column(z.number().int()).generated(),
    firstName: z.string().trim().min(1),
    age: z.number().int().nullable().optional(),
    status: z.enum(['active', 'inactive']).default('active'),
    parentId: column(z.number().nullable()).references('Person', 'id', { inverse: 'children' }),
  },
  modifiers: { adults: q => q.where('age', '>=', 18) },
});

const Animal = defineModel({
  table: 'animals',
  columns: {
    id: column(z.number()).generated(),
    name: z.string(),
    ownerId: column(z.number()).references('Person', 'id', { inverse: 'pets' }),
  },
});

export const db = defineModels({ Person, Animal });

const people = await db.Person.query()
  .select('id', 'firstName')
  .where('age', '>', 18)
  .withGraphFetched('[pets, parent.children]');
// { id: number; firstName: string; pets: Animal[]; parent: (Person & { children: Person[] }) | null }[]
```

## Requirements

|            |                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| objection  | `^3.0.0` (peer dependency). Tested against 3.0.0, 3.1.5, 3.5.0 and 3.9.1 (`pnpm run test:objection-versions`). objection 4.x isn't supported yet. |
| Node       | ≥ 18; tests run on Node 18–24.                                                                                                                    |
| TypeScript | ≥ 5.0 for the typings (tests use 5.8). objection 3.0.x's own declarations need `skipLibCheck` on TypeScript 5.8.                                  |
| Schemas    | Any Standard Schema library. Runtime has no schema-library dependency. Validation must be synchronous.                                            |
| Databases  | Tested on sqlite, Postgres and MySQL. On Postgres, see [bigint ids](#postgres-bigint-ids).                                                        |

## CommonJS and ES modules

Both work, with types for each (checked with `@arethetypeswrong/cli` for `node10`, `node16` from CJS,
`node16` from ESM and `bundler` resolution):

```js
const { defineModel, defineModels } = require('objection-schema'); // CommonJS
```

```js
import { defineModel, defineModels } from 'objection-schema'; // ES modules
```

The ES module entry point re-exports the CommonJS implementation instead of being a second copy,
so an app that mixes `require` and `import` gets one instance (no dual package hazard).
objection 3.x is CommonJS either way.

Since the repo is private, install it from a [GitHub release](https://github.com/br0p0p/objection-schema/releases):
each one has the packed, built package attached. Download it with an authenticated
[GitHub CLI](https://cli.github.com) and install the file:

```bash
gh release download v0.1.0 --repo br0p0p/objection-schema --pattern '*.tgz'
npm install ./objection-schema-0.1.0.tgz   # or: pnpm add ./objection-schema-0.1.0.tgz
```

Commit the `.tgz` (e.g. in `vendor/`) so installs don't need GitHub access. Installing from the
git repository itself doesn't work: it has the TypeScript source, not the build.

## Columns

<!-- eslint-skip -->

```ts
columns: {
  id: column(z.number()).generated(),       // generated by the DB: optional on insert
  createdAt: column(z.date()).hasDefault(), // DB default: optional on insert
  meta: column(Meta).json(),                // stored as JSON (parsed/stringified for you)
  email: z.string().email(),                // a plain schema is a column too
  legacy: unchecked<string>(),              // type only, no runtime validation
  ownerId: column(z.number()).references('Person', 'id', { as: 'owner', inverse: 'pets' }),
}
```

Whether a column is required on insert comes from its schema: when the definition is created, each
schema is probed once with `undefined`. Failure means required, a value means a default (zod
`.default()`), and `undefined` means optional. That's the same rule as the inferred `Insert` type
(`undefined extends Input` ⇒ optional), so runtime and types agree.

## Relations

Relations live outside `defineModel()`: putting them inline with `() => Model` thunks makes
TypeScript type mutually- or self-referencing models as `any` (TS7022). There are three ways to
declare them, and they can be mixed in one registry.

<!-- eslint-skip -->

```ts
// 1. Foreign keys on columns: a belongsToOne (named by `as`, or the column name without
//    `Id`/`_id`), plus an inverse on the target only when `inverse` is given.
vetId: column(z.number().nullable()).references('Vet', 'id', { as: 'doctor', inverse: { name: 'patient', kind: 'one' } }),

// 2. Declarations next to a model; targets are models (definitions or classic classes).
//    The callback runs inside defineModels, so circular imports between model files are safe.
export const personRelations = relations(Person, (r) => ({
  movies: r.manyToMany(Movie, {
    from: 'id',
    to: 'id',
    through: { table: 'persons_movies', from: 'personId', to: 'movieId', extra: { role: z.string() } },
  }),
}));

// 3. A keyed object with registry names.
export const db = defineModels({ Person, Animal, Vet, Movie }, [personRelations], {
  Vet: (r) => ({ colleagues: r.hasMany('Vet', { from: 'clinicId', to: 'clinicId' }) }),
});
```

All five objection relation kinds are available: `hasMany`, `hasOne`, `belongsToOne`,
`manyToMany` and `hasOneThrough`. Each takes single or composite `from`/`to` keys, `modify`, and
`beforeInsert`.

**Rules.** These are compile errors on the `defineModels` call, and `defineModels` throws them at
runtime too, naming both definition sites:

- defining a relation name twice for a model, from any combination of sources;
- naming a relation like one of the model's columns;
- `references()` to an unknown model or column, without a derivable name, or adding an inverse to a
  classic model;
- `relations()` for a model, or targeting a model, that isn't in the registry.

A definition belongs to one registry: its relations are set on its model class, so passing it to a
second `defineModels` call (or twice to one) throws at runtime. Call `defineModel()` again for
another registry, e.g. in tests.

**Checking `references()` targets where they're written.** Declare the registry's names once. They
can't be derived from the registry itself, whose type depends on these columns:

```ts
// models/schema.ts
export const { column } = defineModelNames('Person', 'Animal', 'Vet', 'Movie');
// elsewhere: 'Persn' is now a compile error on the column, names autocomplete,
// and the runtime throws when the column is created.
```

## Interop with class-based models

|                               |                                                                                                                                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Classic models in a registry  | `defineModels({ Person, Movie })`. `db.Movie.query()` gets the typed query API; row types come from the class's fields, and model-typed fields (`actors?: Person[]`) become typed relations. |
| Relations to classic models   | Any of the three styles can target a classic class.                                                                                                                                          |
| Classic models → definitions  | Use the generated class: `modelClass: () => db.Person.modelClass` in `relationMappings`.                                                                                                     |
| Classic models' own relations | Stay in `relationMappings`; the new API can't add relations to classic models.                                                                                                               |
| Results                       | Real model instances (`$relatedQuery`, `toJSON`, … work), typed as plain rows.                                                                                                               |
| Graphs                        | `insertGraph`, `upsertGraph`, `withGraphFetched`, `withGraphJoined` across both kinds.                                                                                                       |
| Infrastructure                | Global `Model.knex(knex)`, `transaction()`, `query(trx)`, `bindKnex()`, `ValidationError` / `NotFoundError`. Plugins and mixins via `defineModel({ base: mixin(Model, [plugin]) })`.         |
| Escape hatch                  | `toQueryBuilder(query)` gives the full classic `QueryBuilder` type.                                                                                                                          |

### Incremental migration

Keep existing hooks and serializers with `defineModel({ base: ExistingModel, table, columns })`.
The generated subclass shadows getter-only statics without changing the original class. Per-model
statics the base reads (`deleteType`, `jsonSchema`, …) go in [`statics`](#statics), not in a
subclass of the base.
Declare JSON columns explicitly, including attributes absent from the old `jsonSchema`.
When new relations are declared, they replace the inherited `relationMappings`, rather than
merging with it. Omitted config hooks remain inherited; configured hooks replace the base's
hook of the same name (they aren't automatically chained).

`modelClass` is typed from the base, so existing code that takes the class keeps working without
casts: it has the base's own statics (`Pet.modelClass.deleteType`), and its instances
(`new Pet.modelClass()`, `InstanceType<typeof Pet.modelClass>`, `Pet.modelClass.query()`, a
custom query builder of the base) have the base's members plus the row. Where the base declares a
field with a type the column's values don't fit (e.g. `id!: string` for a `z.number()` column),
the column wins (objection's `this`-typed members, such as `query()` and `$query()`, then fall back
to the base's instance type). The same holds for `db.Pet.modelClass` and `Pet.bindKnex(knex).modelClass`. A
classic model in a registry gets `ModelClass<Movie>`, without its own statics.

Hooks receive the model instance, and their `row` is typed so: the base's members (objection's
`Model` without a `base`) plus the row, with the row fields partial in the update and delete
hooks, so `row.$query()` or a base method needs no cast.

### Statics

Set statics on the generated class with `statics`, instead of writing a one-off subclass of the
base for each model. They are defined as own properties (like class fields), so they shadow
getter-only statics of a base without changing it:

```ts
const Pet = defineModel({
  base: AppModel,
  table: 'pets',
  columns,
  statics: {
    virtualAttributes: ['label'], // objection's statics are type-checked
    deleteType: 'soft', // custom statics, read by a base class, a plugin or repositories
    jsonSchema: legacyJsonSchema(columns),
  },
});

Pet.modelClass.deleteType; // 'soft', also on db.Pet.modelClass and Pet.bindKnex(knex).modelClass
```

- **objection's statics** (`virtualAttributes`, `useLimitInFirst`, `defaultGraphOptions`,
  `jsonSchema`, `QueryBuilder`, `createNotFoundError`, `concurrency`, …) are checked against
  objection's types. Instance members, such as the getters `virtualAttributes` names, come from
  the `base`.
- **Custom statics** (`deleteType`, `softDeleteKey`, …) are kept on `modelClass`, and in its type
  with their literal types. One that the base declares has to fit the base's type.
- **Rejected** (compile errors, and errors when the definition is created): the keys the library
  sets itself (`tableName` from `table`, `idColumn` from `id`, `modifiers`, `jsonAttributes` and
  `createValidator` from `columns` and `validate`, `name`, and `relationMappings`, which
  `defineModels()` sets from the declared relations; classic relations go on a `base`),
  `prototype`, `columnNameMappers` (see [Known limitations](#known-limitations)), and objection's
  other statics, e.g. `query`, `knex`, `fromJson` and the static query hooks
  (`static beforeInsert`, …), which would replace objection's or the base's: put those on a `base`.
  Symbol keys are rejected too: statics need string keys.
- **`jsonSchema`** doesn't validate (the column schemas do), but with
  `pickJsonSchemaProperties: true` objection keeps only the `jsonSchema` properties when it writes
  rows, so columns missing from a legacy schema would be dropped from inserts and updates.
- **`QueryBuilder`:** a custom query builder's extra methods work at runtime, but the typed query
  API doesn't know them. Use `toQueryBuilder(query)`, or `Pet.modelClass.query()`, which is typed
  from a base's custom query builder.

App-level `defineModel` wrappers can name the option's type as `ModelStatics`.

[Real-app migration probes](tests/migrations/README.md) document pinned Wiki.js and Conduit
sources, executable migration slices, adaptations and bugs found. These are incremental
model/query migrations to Objection 3, not full application ports.

## Validation

Each column is validated with its own schema on `insert`, `insertGraph`, `upsertGraph`, `update`,
`patch` and `fromJson`, following objection's rules. Rows read from the database aren't validated.

- **Patch** validates only the keys you pass. No `.partial()` copy of a schema is needed.
- **Schema output is what's stored**, so trimming, lowercasing, coercion and defaults apply.
- **Errors** are objection's `ValidationError` (status 400), with Ajv-compatible `data` keys,
  including nested and graph paths (`address.city`, `pets[1].name`). `keyword` is the library name
  and `params.issue` is the original issue.
- **Without a database:** `Person.validate(body)` and `Person.validate(body, { patch: true })`
  return the parsed output.
- **Reuse schemas:** `z.object({ email: Person.columns.email })`. Columns wrapped in `column()`
  expose `.schema`.
- **Opt out** per call (`{ skipValidation: true }`), per model (`validate: false`), or per column
  (`unchecked<T>()`).
- **Async rules** (uniqueness, lookups) go in async `hooks.beforeInsert` / `beforeUpdate`. Async
  schemas are rejected with a clear error, because objection's validation is synchronous.
- **Graph writes** validate node by node, as objection does. Wrap `insertGraph` / `upsertGraph` in a
  transaction if a failure partway through shouldn't leave earlier rows behind.

## Type safety and editor support

- `Row`, `Insert`, `Patch` and `Result` helper types: `Row<typeof db.Person>`.
- `select` narrows (with `'col as alias'`), and `where` / `whereIn` / `orderBy` check column names
  and value types.
- `findById` takes the id's type, including tuples for composite ids. `first()` / `findById()`
  return `T | undefined`, and `throwIfNotFound()` removes the `undefined`.
- Relation expressions in object or string form (`'[pets.owner, children(adults)]'`) are checked and
  typed. `modifyGraph` paths are checked and its callback is typed for the target model.
- Joined columns (`pets.name`, `parent:pets.name`) are typed after `joinRelated` / `withGraphJoined`.
- `insertGraph` / `upsertGraph` inputs are checked deeply, with child foreign keys filled in.
- Errors list the valid names (`'"agee"' is not assignable to '"id" | "firstName" | …'`), and
  completions work for columns, relation paths, relation targets and insert fields
  (`pnpm run bench:completions`).

## Performance

Run `pnpm run bench`, `bench:validation` and `bench:typecheck`. Measured on Node 22 with objection
3.1.5–3.9.1:

- **Reads:** same speed as classic models. Nothing is validated on the way out.
- **Validation** (µs per row, insert):

  | schema                                            | none | Ajv (classic) |  zod | valibot |
  | ------------------------------------------------- | ---: | ------------: | ---: | ------: |
  | simple                                            | 0.97 |          2.01 | 1.26 |    1.21 |
  | realistic (email, url, regex, transforms, refine) | 1.34 |          5.46 | 6.29 |    4.13 |

  That's about 2–3% of a single in-memory sqlite insert. It matters for bulk imports, where the opt-outs above help.

- **Startup:** `require('zod')` takes ~80 ms. `defineModel()` takes ~0.5 ms per 10-column model.
- **Type-checking** a registry: 0.5 s at 10 models, 1.3 s at 40, 3.1 s at 80 (`skipLibCheck`).
  Inferring through zod costs about the same as hand-written types.

## Known limitations

- **Read types vs. database types:** row types are the schemas' _output_ types, but rows from the
  database aren't run through the schemas. E.g. `z.date()` on sqlite (a string or number), or
  `decimal`/`numeric` columns, which Postgres and MySQL return as strings.
- <a id="postgres-bigint-ids"></a>**Postgres `bigint` ids:** `pg` returns `bigint` (`bigIncrements`)
  as strings. Besides the read type, this breaks graph writes: `insertGraph` and `upsertGraph` copy
  the parent's string id into a child's foreign key, and a `z.number()` schema rejects it. Either
  parse `bigint` as a number, which is exact up to `Number.MAX_SAFE_INTEGER`:

  ```js
  require('pg').types.setTypeParser(20, Number); // or per connection: `connection.types`
  ```

  or use `z.coerce.number()` for id and foreign key columns (ids read from the database are then
  still strings).

- **Column naming:** property names are column names. For snake_case use knex's
  `knexSnakeCaseMappers()`; per-model casing needs a hook in objection. `statics` rejects
  `columnNameMappers`: ids, relation joins and typed queries use property names as column names,
  so it would break them.
- **Untyped query methods:** aggregates, raw/subquery selects, JSON operators and unions. Use
  `toQueryBuilder(query)` for these.
- **Joined columns:** `leftJoinRelated` / `withGraphJoined` columns aren't typed as nullable yet.
- **Graph foreign keys:** in graph inputs, a `belongsToOne` owner's foreign key is still required
  when the related row is inserted in the same graph.
- **Model-level rules:** there are no cross-field rules (`refine(row)`) and no async validation in
  schemas.

## Development

The toolchain (Node and pnpm versions) is pinned in `mise.toml`; install [mise](https://mise.jdx.dev) and
run `mise install`.

The source is TypeScript in `lib/`, built with `tsc` into `dist/` (CommonJS, the ES module entry
and the declarations), which is what the package publishes and what the tests run against.

```bash
mise install
pnpm install
pnpm run check                   # lint (which includes formatting), then pnpm test: run this before pushing
pnpm run build                   # lib/ -> dist/ (the test scripts build first on their own)
pnpm test                        # runtime (CJS + ESM), types (node10 + nodenext), package exports
pnpm run test:pg                 # runtime tests on Postgres (DB=pg; PG* variables, see tests/runtime/db.js)
pnpm run test:mysql              # runtime tests on MySQL (DB=mysql; MYSQL_* variables)
pnpm run test:pack               # the packed package installed in a fresh app (CJS, ESM, TypeScript)
pnpm run test:objection-versions # runtime + types against several objection 3.x releases
pnpm run test:mutations          # Stryker mutation testing of lib/ (must stay at 100%)
pnpm run test:mutations:types    # curated mutants of the type declarations (all must be caught)
pnpm run lint:fix                # fix lint findings and format (ESLint, antfu's config)
pnpm run lint:anti-slop          # additional anti-slop policy audit
```

[Anti-slop](https://github.com/dmmulroy/anti-slop) is vendored in `tools/oxlint/anti-slop/`,
with matching, exact Oxlint dependencies and generic rules configured in `.oxlintrc.json`.
The `no-runtime-typeof` rule is intentionally off: runtime type checks are legitimate in this
validation library. For now, `no-object-parameters`, `no-unknown-parameters`, and
`no-unsafe-dictionary-type` are also off to preserve the library's public type contracts.
All other generic rules remain enabled. ESLint remains the formatter and existing lint gate;
anti-slop is a separate audit, not part of `check` or CI. The configured audit passes after safe
fixes and these policy adjustments; runtime behavior and public type contracts are unchanged.
See the vendored
[provenance and baseline](tools/oxlint/anti-slop/UPSTREAM.md) for details and update guidance.

The invariants that changes must keep (runtime/types parity, Node 18 support, the 100% mutation
score, …) and the workflow for making a change are in [AGENTS.md](AGENTS.md), which is also what
coding agents read. `CLAUDE.md` and `.claude/` configure Claude Code for this repo.

How the tests are layered:

- **Example tests** (`tests/runtime/*.test.js`) cover each feature, its errors, and interop with
  class-based models and objection's APIs (`interop.test.js`). They run on in-memory sqlite by
  default, and in CI also on Postgres and MySQL (`DB=pg|mysql`). `databases.test.js` uses the
  column types of real applications (bigint ids, decimals, JSON, timestamps, arrays).
- **Package test** (`scripts/test-pack.js`) installs the packed package into a fresh project with
  its own objection, checks the package's files, and runs an app from CommonJS, ES modules and
  TypeScript (`nodenext`).
- **Property tests** (`tests/runtime/properties.test.js`, [fast-check](https://fast-check.dev))
  check rules against independent oracles. Validation must agree with an equivalent zod object
  schema for any input, never mutate its input, be idempotent, and leave patches alone. Rows must
  round-trip through the database. Relation merging must match a model of the rules for random
  registries. Guard tests keep the generated inputs balanced between valid and invalid.
  `FC_NUM_RUNS` scales the number of runs.
- **Type tests** (`tests/types`) assert exact inferred types and expected errors, and pin the
  exact messages of relation errors via the `RelationErrors` type. They compile against the built
  declarations in `dist/`, as users do.
- **Mutation tests:**
  - Stryker mutates `lib/`; every mutant must be killed. The few behaviour-equivalent mutants
    (performance-only differences) are disabled in place, with the reason next to the code.
  - `scripts/mutate-types.js` does the same for the type declarations, which Stryker can't mutate.
  - Mutation testing runs in CI on pull requests (`.github/workflows/mutation.yml`).

If `sqlite3` fails to build (old `node-gyp` vs. Python ≥ 3.12), run
`pnpm install --ignore-scripts`, then `cd node_modules/sqlite3 && pnpm dlx node-gyp@latest rebuild`.
