# objection-schema

Schema-first, class-free models for [objection.js](https://vincit.github.io/objection.js) 3.x.
Columns are [Standard Schema](https://standardschema.dev) validators (zod, valibot, arktype, …), and
row, insert, patch, relation and query result types are inferred from them. Under the hood each
definition is an ordinary objection `Model` subclass, so it works with existing class-based models,
query builders, transactions and plugins.

> **Status:** 0.1.0, private, exploratory. It grew out of an exploration branch of objection itself;
> the design notes and history are in the `objection-typed-exploration` repo (PR #1).

```ts
import { z } from 'zod';
import { defineModel, defineModels, column } from 'objection-schema';

const Person = defineModel({
  table: 'persons',
  columns: {
    id: column(z.number().int()).generated(),
    firstName: z.string().trim().min(1),
    age: z.number().int().nullable().optional(),
    status: z.enum(['active', 'inactive']).default('active'),
    parentId: column(z.number().nullable()).references('Person', 'id', { inverse: 'children' }),
  },
  modifiers: { adults: (q) => q.where('age', '>=', 18) },
});

const Animal = defineModel({
  table: 'animals',
  columns: {
    id: column(z.number()).generated(),
    name: z.string(),
    ownerId: column(z.number()).references('Person', 'id', { inverse: 'pets' }),
  },
});

export const db = defineModels({ Person, Animal });

const people = await db.Person.query()
  .select('id', 'firstName')
  .where('age', '>', 18)
  .withGraphFetched('[pets, parent.children]');
// { id: number; firstName: string; pets: Animal[]; parent: (Person & { children: Person[] }) | null }[]
```

## Requirements

|            |                                                                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| objection  | `^3.0.0` (peer dependency). Tested against 3.0.0, 3.1.5, 3.5.0 and 3.9.1 (`npm run test:objection-versions`). objection 4.x isn't supported yet. |
| Node       | Same as objection 3 (≥ 14) for the runtime; tests run on Node 18–22.                                                                             |
| TypeScript | ≥ 5.0 for the typings (tests use 5.8). objection 3.0.x's own declarations need `skipLibCheck` on TypeScript 5.8.                                 |
| Schemas    | Any Standard Schema library. Runtime has no schema-library dependency. Validation must be synchronous.                                           |

## CommonJS and ES modules

Both work, with types for each (checked with `@arethetypeswrong/cli` for `node10`, `node16` from CJS,
`node16` from ESM and `bundler` resolution):

```js
const { defineModel, defineModels } = require('objection-schema'); // CommonJS
```

```js
import { defineModel, defineModels } from 'objection-schema'; // ES modules
```

The ES module entry point re-exports the CommonJS implementation instead of being a second copy,
so an app that mixes `require` and `import` gets one instance (no dual package hazard).
objection 3.x is CommonJS either way.

Since the repo is private, install it from GitHub with an authenticated git setup:
`npm install github:br0p0p/objection-schema`.

## Columns

```ts
columns: {
  id: column(z.number()).generated(),       // generated by the DB: optional on insert
  createdAt: column(z.date()).hasDefault(), // DB default: optional on insert
  meta: column(Meta).json(),                // stored as JSON (parsed/stringified for you)
  email: z.string().email(),                // a plain schema is a column too
  legacy: unchecked<string>(),              // type only, no runtime validation
  ownerId: column(z.number()).references('Person', 'id', { as: 'owner', inverse: 'pets' }),
}
```

Whether a column is required on insert comes from its schema: when the definition is created, each
schema is probed once with `undefined`. Failure means required, a value means a default (zod
`.default()`), and `undefined` means optional. That's the same rule as the inferred `Insert` type
(`undefined extends Input` ⇒ optional), so runtime and types agree.

## Relations

Relations live outside `defineModel()`: putting them inline with `() => Model` thunks makes
TypeScript type mutually- or self-referencing models as `any` (TS7022). There are three ways to
declare them, and they can be mixed in one registry.

```ts
// 1. Foreign keys on columns: a belongsToOne (named by `as`, or the column name without
//    `Id`/`_id`), plus an inverse on the target only when `inverse` is given.
vetId: column(z.number().nullable()).references('Vet', 'id', { as: 'doctor', inverse: { name: 'patient', kind: 'one' } }),

// 2. Declarations next to a model; targets are models (definitions or classic classes).
//    The callback runs inside defineModels, so circular imports between model files are safe.
export const personRelations = relations(Person, (r) => ({
  movies: r.manyToMany(Movie, {
    from: 'id',
    to: 'id',
    through: { table: 'persons_movies', from: 'personId', to: 'movieId', extra: { role: z.string() } },
  }),
}));

// 3. A keyed object with registry names.
export const db = defineModels({ Person, Animal, Vet, Movie }, [personRelations], {
  Vet: (r) => ({ colleagues: r.hasMany('Vet', { from: 'clinicId', to: 'clinicId' }) }),
});
```

All five objection relation kinds are available: `hasMany`, `hasOne`, `belongsToOne`,
`manyToMany` and `hasOneThrough`. Each takes single or composite `from`/`to` keys, `modify`, and
`beforeInsert`.

**Rules.** These are compile errors on the `defineModels` call, and `defineModels` throws them at
runtime too, naming both definition sites:

- defining a relation name twice for a model, from any combination of sources;
- naming a relation like one of the model's columns;
- `references()` to an unknown model or column, without a derivable name, or adding an inverse to a
  classic model;
- `relations()` for a model, or targeting a model, that isn't in the registry.

**Checking `references()` targets where they're written.** Declare the registry's names once. They
can't be derived from the registry itself, whose type depends on these columns:

```ts
// models/schema.ts
export const { column } = defineModelNames('Person', 'Animal', 'Vet', 'Movie');
// elsewhere: 'Persn' is now a compile error on the column, names autocomplete,
// and the runtime throws when the column is created.
```

## Interop with class-based models

|                               |                                                                                                                                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Classic models in a registry  | `defineModels({ Person, Movie })`. `db.Movie.query()` gets the typed query API; row types come from the class's fields, and model-typed fields (`actors?: Person[]`) become typed relations. |
| Relations to classic models   | Any of the three styles can target a classic class.                                                                                                                                          |
| Classic models → definitions  | Use the generated class: `modelClass: () => db.Person.modelClass` in `relationMappings`.                                                                                                     |
| Classic models' own relations | Stay in `relationMappings`; the new API can't add relations to classic models.                                                                                                               |
| Results                       | Real model instances (`$relatedQuery`, `toJSON`, … work), typed as plain rows.                                                                                                               |
| Graphs                        | `insertGraph`, `upsertGraph`, `withGraphFetched`, `withGraphJoined` across both kinds.                                                                                                       |
| Infrastructure                | Global `Model.knex(knex)`, `transaction()`, `query(trx)`, `bindKnex()`, `ValidationError` / `NotFoundError`. Plugins and mixins via `defineModel({ base: mixin(Model, [plugin]) })`.         |
| Escape hatch                  | `toQueryBuilder(query)` gives the full classic `QueryBuilder` type.                                                                                                                          |

## Validation

Each column is validated with its own schema on `insert`, `insertGraph`, `upsertGraph`, `update`,
`patch` and `fromJson`, following objection's rules. Rows read from the database aren't validated.

- **Patch** validates only the keys you pass. No `.partial()` copy of a schema is needed.
- **Schema output is what's stored**, so trimming, lowercasing, coercion and defaults apply.
- **Errors** are objection's `ValidationError` (status 400), with Ajv-compatible `data` keys,
  including nested and graph paths (`address.city`, `pets[1].name`). `keyword` is the library name
  and `params.issue` is the original issue.
- **Without a database:** `Person.validate(body)` and `Person.validate(body, { patch: true })`
  return the parsed output.
- **Reuse schemas:** `z.object({ email: Person.columns.email })`. Columns wrapped in `column()`
  expose `.schema`.
- **Opt out** per call (`{ skipValidation: true }`), per model (`validate: false`), or per column
  (`unchecked<T>()`).
- **Async rules** (uniqueness, lookups) go in async `hooks.beforeInsert` / `beforeUpdate`. Async
  schemas are rejected with a clear error, because objection's validation is synchronous.
- **Graph writes** validate node by node, as objection does. Wrap `insertGraph` / `upsertGraph` in a
  transaction if a failure partway through shouldn't leave earlier rows behind.

## Type safety and editor support

- `Row`, `Insert`, `Patch` and `Result` helper types: `Row<typeof db.Person>`.
- `select` narrows (with `'col as alias'`), and `where` / `whereIn` / `orderBy` check column names
  and value types.
- `findById` takes the id's type, including tuples for composite ids. `first()` / `findById()`
  return `T | undefined`, and `throwIfNotFound()` removes the `undefined`.
- Relation expressions in object or string form (`'[pets.owner, children(adults)]'`) are checked and
  typed. `modifyGraph` paths are checked and its callback is typed for the target model.
- Joined columns (`pets.name`, `parent:pets.name`) are typed after `joinRelated` / `withGraphJoined`.
- `insertGraph` / `upsertGraph` inputs are checked deeply, with child foreign keys filled in.
- Errors list the valid names (`'"agee"' is not assignable to '"id" | "firstName" | …'`), and
  completions work for columns, relation paths, relation targets and insert fields
  (`npm run bench:completions`).

## Performance

Run `npm run bench`, `bench:validation` and `bench:typecheck`. Measured on Node 22 with objection
3.1.5–3.9.1:

- **Reads:** same speed as classic models. Nothing is validated on the way out.
- **Validation** (µs per row, insert):

  | schema                                            | none | Ajv (classic) |  zod | valibot |
  | ------------------------------------------------- | ---: | ------------: | ---: | ------: |
  | simple                                            | 0.97 |          2.01 | 1.26 |    1.21 |
  | realistic (email, url, regex, transforms, refine) | 1.34 |          5.46 | 6.29 |    4.13 |

  That's about 2–3% of a single in-memory sqlite insert. It matters for bulk imports, where the opt-outs above help.

- **Startup:** `require('zod')` takes ~80 ms. `defineModel()` takes ~0.5 ms per 10-column model.
- **Type-checking** a registry: 0.5 s at 10 models, 1.3 s at 40, 3.1 s at 80 (`skipLibCheck`).
  Inferring through zod costs about the same as hand-written types.

## Known limitations

- **Read types vs. database types:** row types are the schemas' _output_ types, but rows from the
  database aren't run through the schemas. E.g. `z.date()` on sqlite, or Postgres
  `bigint`/`numeric` read as strings.
- **Column naming:** property names are column names. For snake_case use knex's
  `knexSnakeCaseMappers()`; per-model casing needs a hook in objection.
- **Untyped query methods:** aggregates, raw/subquery selects, JSON operators and unions. Use
  `toQueryBuilder(query)` for these.
- **Joined columns:** `leftJoinRelated` / `withGraphJoined` columns aren't typed as nullable yet.
- **Graph foreign keys:** in graph inputs, a `belongsToOne` owner's foreign key is still required
  when the related row is inserted in the same graph.
- **Model-level rules:** there are no cross-field rules (`refine(row)`) and no async validation in
  schemas.
